# Compiling handoff for Oleksandr

The current contract is `src/core.hpp`; the executable consumes `sampleLessons()` and `comparisons()` from `src/sample_content.cpp`. These functions currently return three starter lessons and three comparisons. The variables record is now sourced from `cwaypoint::variablesLesson()` through `src/lesson_adapter.cpp`; extend that authored source through an explicitly reviewed mapping rather than duplicating its text. The C++ strings and C pointers records remain in `sample_content.cpp`. The complete curriculum remains 14 lessons; do not add placeholder lessons to completion totals.

Each lesson has a unique ID, `C` or `C++` track, title, objective, explanation, example code and positive assessment revision. Its three questions are ordered as two practice questions and one initially unseen fresh check. Each question has a globally unique ID, prompt, accepted answer, question type, explanation and exactly three authored hint levels. Choice questions also have their choices; the accepted answer must match one of them. `validate()` rejects invalid required records at startup. Optional empty walkthroughs have no player.

The evaluator is the only correctness authority. `evaluate()` returns Correct, Incorrect or Invalid and feedback. Output questions normalize CRLF to LF and ignore at most one final newline; spaces and case otherwise matter. Token and choice answers trim outer whitespace then compare exactly. Empty input is Invalid and consumes no attempt. Input is limited to 1,024 bytes.

The controller owns issuance, attempts, assistance, practice completion and review membership. The UI calls `issue`, `help`, `submit`, `retry`, `resume` and `reset`. Successful first-attempt evidence is historical: later hints or retries do not erase it. Wrong answers enter mistake review; a correct retry clears review without manufacturing a new first attempt. Practice completion counts only the two practice records. Fresh-check status is separate.

The storage owner writes versioned snapshots under a current-generation manifest. `flock` permits one writer; second instances use temporary practice. New fresh-check issuance must be saved before displaying it. Help is recorded before a hint or reveal is shown; failed write barriers block display in a writable profile. Corrupt primary recovery from the same-generation backup marks first-attempt history unverified. Unsupported/corrupt/unreadable saves are preserved. Writes and resets are synchronous and serialized on the main thread in this increment; no pending background writer exists.

No AI requests or worker are implemented yet. Keep future provider results immutable and tagged with lesson/assessment revision, question ID, answer revision, hint level, provider configuration generation, profile generation and request ID. Only the controller should apply matching results. Provider choice, credentials, approved networking dependency, bounded cancellation and failure fixtures remain Oleksandr's integration work. The current UI explicitly states that AI is not configured and provides authored offline hints.

Build with CMake and run CTest before changing the contract. Update producer, evaluator, controller tests and UI together when changing fields or semantics. Current tests are examples for the shared contract, not acceptance of the full reviewed test plan.

Optional teaching records are checked by `validateWalkthrough()` and `validateComparison()` at their consuming views. Walkthroughs allow 1–32 complete steps, with per-field and aggregate text limits; an absent walkthrough remains optional. Invalid optional data disables only that view. `Controller::solved()` and `nextLesson()` derive practice status and same-track recommendations from the existing evidence; do not implement separate UI completion counters.

`Controller::reviewItems(track)` returns current lesson/question indices in catalogue order, with an optional C/C++ filter. Review screens consume this projection rather than the raw persisted ID set. On assessment revision changes, issuance resets obsolete review membership alongside its evidence. Successful retries still use `submit()`; review has no separate correctness or completion rules.

Snapshot format two appends `RESUME question walkthrough assessmentRevision` after evidence records and before END. Format-one reads remain supported with default positions. `Controller::resume(lesson, stage, question, walkthrough)` validates/canonicalizes positions; all UI navigation uses it. Walkthrough indexes are checked against current records at load, and assessment revision changes restart the explanation. Draft answer text is not part of this persisted contract. Manifest version/generation semantics are unchanged.

The first authored adapter maps author revision 1 to graphical assessment revision 2, retaining the established graphical lesson/question IDs. It accepts only the checked-in variables record shape: one accepted answer, exactly three hints, output/token types and two practice questions followed by the fresh check. Unsupported shapes or changed author revisions fail clearly at startup. The first question is now output entry rather than choice. The fresh check uses the authored copy-of-value example. Revision-1 graphical evidence is not reassigned to these revised assessments; existing controller projections exclude it. See `docs/integration.md` for the explicit ID mapping.

`Question::code` is optional question-specific teaching context (maximum 8192 bytes). An empty value falls back to the lesson example. Fresh-check examples are explicit records rather than parsed from prompts; this presentation addition does not change accepted answers or assessment meaning. `Controller::unsavedChanges` exposes the last persistence failure for save-recovery UI; success clears it. It is session state, not a new snapshot field.
